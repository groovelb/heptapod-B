## D-01. 공개 범위 — 비회원 열람 경계

### 결정 사항

비회원(비로그인) 사용자가 Archive의 어디까지 열람할 수 있는가?

### 문서에서 언급된 제약

- "인코딩·분석·PNG 저장은 비회원도 사용할 수 있다" (공개·권한 계약)
- "공개 Glyph와 공개 관계는 비회원도 읽을 수 있다" (공개·권한 계약)
- "인증은 PUBLISH, BOOKMARK, REPORT, UNPUBLISH에서만 요구한다" (공개·권한 계약)
- Resonance Field, Response Detail 페이지의 인증 칸: "읽기 불필요" (페이지 리스트)

### 선택지

| 옵션 | 비회원 열람 범위 | 장점 | 단점 |
|---|---|---|---|
| **A. 전면 공개 (권장)** | 인코딩 + Resonance Field + Glyph Detail + The Real Story 전체 열람 가능. 로그인 필요 시점은 PUBLISH/BOOKMARK/REPORT/UNPUBLISH만 | 진입 장벽 최소, 세계관 몰입 우선 | 크롤링·스크래핑 노출 |
| B. 지도 제한 | 인코딩·Glyph Detail은 공개, Resonance Field는 로그인 후 | 핵심 콘텐츠에 인증 게이트로 전환율↑ | 탐색 맥락 끊김, "한 장면" 원칙 위반 가능 |
| C. 미리보기 | Field/Detail 각각 관계 3개까지만 비회원 공개, 전체는 로그인 후 | 핵심 콘텐츠에 인증 게이트, 맛보기 가능 | 구현 복잡도↑, "억지 연결하지 않는다" 원칙과 부분 공개 조합이 혼란 |

### 권장안

**A. 전면 공개.** 문서가 이미 "읽기 불필요"를 명시하고, 내러티브 원칙 1("하나의 장면")은 탐색 흐름의 연속성을 요구한다. 인증 게이트는 쓰기 행위에만 둔다.

### 후속 영향

- Schema/RLS (Gate 4): `glyphs`, `glyph_relations`에 `anon` 읽기 RLS 필요
- Component (Gate 5): Resonance Field에 로그인 유도 UI 불필요 → 단순화

## D-02. 동일 이름 병합 정책 — canonical 충돌 시 UX

### 결정 사항

사용자가 PUBLISH하려는 이름의 canonical fingerprint가 이미 존재할 때 어떤 경험을 주는가?

### 문서에서 언급된 제약

- "같은 canonical name과 encoder version이 이미 있으면 기존 Glyph에 기여를 추가하고, 없으면 새 Glyph 생성" (시나리오 5, 플로우 6)
- "이미 본인이 공개한 동일 Glyph → 중복 contribution을 만들지 않고 기존 상세로 이동" (시나리오 5, 예외)
- "동일 fingerprint는 새 Glyph를 만들지 않고 기존 노드로 합친다" (데이터 모델 카드 B)
- "사용자의 원래 표기는 contribution 문맥에서만 보존" (정규화 규칙 6)
- 내러티브 원칙 5: "개인보다 집단 발화"

### 선택지

| 옵션 | UX | 장점 | 단점 |
|---|---|---|---|
| **A. 자동 합류 + 안내 (권장)** | "이 이름은 이미 Archive에 있습니다. 당신의 응답을 기여로 추가합니다." → 태그 입력 → 기존 Glyph에 contribution 추가 | 집단 발화 세계관 일관, 중복 방지 | 사용자가 "내 고유 결과"라 느낄 기대와 충돌 가능 |
| B. 선택지 제시 | "이 이름은 이미 있습니다. 기여를 추가하시겠습니까, 아니면 변형을 시도하시겠습니까?" → 합류 또는 의문형 토글 제안 | 사용자 자율성 | "변형 시도" 가 의문형 외에는 없어 실질적 선택이 아님 |
| C. 묵시적 합류 | 별도 안내 없이 기존 Glyph에 contribution 추가, 결과 화면에서 기여자 수 표시 | 마찰 최소 | "내가 최초"라 생각한 사용자가 혼란 |

### 권장안

**A. 자동 합류 + 안내.** 결정론적 인코딩의 핵심은 같은 이름 = 같은 형태이므로 분기할 실질적 변종이 없다. "이미 있는 발화에 당신의 맥락을 더합니다"라는 내러티브로 합류를 긍정적으로 프레이밍한다.

### 후속 영향

- Component (Gate 5): PublishDialog에 "기존 Glyph 합류" 상태 UI가 필요
- Schema (Gate 4): `glyph_contributions`에 같은 user+glyph 유니크 제약

## D-03. Contribution 삭제 cascade

### 결정 사항

사용자가 자신의 contribution을 삭제(unpublish)할 때 Glyph와 관계는 어떻게 처리하는가?

### 문서에서 언급된 제약

- "자신의 contribution만 삭제한다. 마지막 활성 contribution이 제거되면 해당 Glyph와 연결 관계도 공개 지도에서 제거한다" (데이터 모델 카드 C)
- "사용자 공개 취소가 다른 기여자의 데이터에 영향을 주지 않으며" (성공 기준)
- "여러 사용자가 같은 Glyph를 공개한 경우 → 한 사용자의 공개 취소가 다른 기여를 삭제하지 않음" (시나리오 7)

### 선택지

| 옵션 | Glyph 처리 | 관계 처리 | 비고 |
|---|---|---|---|
| **A. 소프트 삭제 + 지연 정리 (권장)** | contribution `status = 'withdrawn'`. 마지막 활성 기여자 없으면 Glyph `status = 'hidden'`. 30일 후 hard delete | Glyph hidden 시 관련 relation도 `status = 'hidden'` | 복구 가능, 운영 안전 |
| B. 즉시 hard delete | contribution 행 삭제. 마지막이면 Glyph + relation 즉시 삭제 | cascade delete | 복구 불가, 단순 |
| C. 영구 보존 | contribution 비활성화만, Glyph는 영구 공개 유지 | 관계 유지 | "삭제 권리" 미충족, GDPR 등 고려 필요 |

### 권장안

**A. 소프트 삭제 + 지연 정리.** 실수 복구 가능성을 확보하면서 마지막 기여자 제거 시 공개 노출을 즉시 중단한다. 30일 유예 후 hard delete로 데이터 최소 보존 원칙을 준수한다.

### 후속 영향

- Schema (Gate 4): contribution·glyph·relation 테이블에 `status` enum과 `withdrawn_at` 타임스탬프 필요
- Data Bridge (Gate 3): 삭제 시 남은 활성 contribution 수 조회 → Glyph status 전환 로직 필요
- Component (Gate 5): MyArchivePage에 "공개 취소" 확인 다이얼로그 + 되돌리기 기간 안내

## D-04. 제한 태그 체계

### 결정 사항

publish 시 선택할 수 있는 context tag의 구체적 목록은 무엇인가?

### 문서에서 언급된 제약

- "정체성·기억·감각·의도 범주의 제한 태그를 최대 3개 선택한다" (CONTEXT 알고리즘)
- "자유 입력 의미를 AI가 추론하지 않는다" (CONTEXT 알고리즘)
- "`사람`, `이름`처럼 거의 모두에게 해당하는 일반 태그는 관계 계산에서 제외한다" (CONTEXT 알고리즘)
- "의미를 아는 척하지 않기" (내러티브 원칙 3)
- TagInput 수정: "자유 태그가 아닌 허용 목록 모드 필요" (컴포넌트 리스트)

### 선택지

| 옵션 | 태그 설계 | 장점 | 단점 |
|---|---|---|---|
| **A. 4범주 × 4~5 태그 = 16~20개 (권장)** | 아래 초안 참조. 범주당 선택 제한 없이 전체에서 최대 3개 | IDF 분산 적절, 구현 단순 | 범주 균형 조정 필요 |
| B. 2단계 (범주 선택 → 하위 태그) | 범주 먼저 고르고 그 안에서 태그 선택 | 태그 발견성↑ | 단계 증가, 모바일 마찰↑ |
| C. 자유 입력 + 운영 승인 | 사용자 자유 입력, 운영진이 태그 정규화 | 표현 자유도 최대 | 운영 비용↑, IDF 계산 불안정, 원칙 3 위반 우려 |

#### 옵션 A 태그 초안

| 범주 | 태그 | 관계 계산 포함 여부 |
|---|---|---|
| **정체성** | `내 이름`, `가족`, `연인·친구`, `반려동물`, `캐릭터·인물` | ✅ (`내 이름`은 IDF 낮아 약한 가중) |
| **기억** | `그리움`, `약속`, `첫 만남`, `이별`, `유산` | ✅ |
| **감각** | `소리`, `풍경`, `촉감`, `향기` | ✅ |
| **의도** | `기록`, `선물`, `질문`, `기도·소망` | ✅ |

> 일반 태그 제외 목록: `사람`, `이름`, `한글`, `영어` — IDF가 너무 낮아 관계 계산에서 제외

### 권장안

**A. 4범주 × 4~5 태그 = 18개 초안.** 위 초안을 시작점으로 하되, 아카이브 초기 500개 이름 단계에서 IDF 분포를 확인하고 태그를 추가/병합한다. 범주는 UI 그루핑용이지 선택 제한은 아니다(어느 범주에서든 총 3개).

### 후속 영향

- Encoder v2 (Gate 2): 태그는 인코딩 로직과 무관 — 영향 없음
- Schema (Gate 4): `glyph_contributions.context_tags`를 text[] 또는 enum[]으로 설계. 허용 목록을 DB check constraint 또는 앱 레벨로 관리
- Component (Gate 5): TagInput 허용 목록 모드 구현, PublishDialog에 범주별 그루핑 UI
- 관계 로직: `scoreContextRelation.js`에 일반 태그 제외 목록 + IDF 계산 대상 목록 하드코딩 또는 config

## D-05. 인증 플로우 — publish 시점 인증 및 Glyph 복귀

### 결정 사항

비로그인 사용자가 PUBLISH를 누른 후 인증 → 복귀하는 구체적 흐름은 무엇인가?

### 문서에서 언급된 제약

- "비로그인 상태면 인증 오버레이 진입. 이름·모델·입력 상태는 로컬에 유지" (시나리오 5, 플로우 2)
- "인증 완료 후 동일한 공개 확인 단계로 복귀" (시나리오 5, 플로우 3)
- "인증 취소 → 인코더 상태로 복귀, 로컬 결과 유지" (시나리오 5, 예외)
- "publish 시작 사용자 중 인증 후 원래 Glyph로 복귀하는 비율" (성공 기준)
- Auth Overlay는 "현재 경로 위 overlay" (페이지 리스트)

### 선택지

| 옵션 | 인증 방식 | 복귀 방식 | 장점 | 단점 |
|---|---|---|---|---|
| **A. 인페이지 오버레이 (권장)** | 현재 페이지 위에 모달로 로그인/가입 | 모달 닫으면 즉시 PublishDialog 복귀. 상태 유실 없음 | 맥락 유지 최강, 구현 단순 | OAuth redirect 시 페이지 이탈 가능 |
| B. 별도 페이지 + state 복원 | `/auth`로 이동, `returnTo` 쿼리에 인코더 상태 직렬화 | 인증 후 redirect로 복원 | OAuth 자연스러움 | URL에 이름 노출 위험, 상태 직렬화 복잡 |
| C. 팝업 윈도우 | `window.open`으로 인증 팝업 | 팝업 닫히면 부모 윈도우가 감지하고 PublishDialog 진입 | 부모 상태 완전 유지 | 팝업 차단기 이슈, 모바일 UX 열악 |

### 권장안

**A. 인페이지 오버레이.** Supabase Auth UI를 모달 안에 임베드. OAuth provider(Google 등) 사용 시 `signInWithOAuth`의 `redirectTo`를 현재 URL + `publishPending=true` 파라미터로 설정하고, 돌아올 때 `sessionStorage`에 저장해 둔 `EncodeSession`을 복원한 뒤 PublishDialog를 자동 재진입한다.

### 후속 영향

- Component (Gate 5): LoginForm/SignUpForm은 모달 내 렌더링 전제, AuthGuard는 publish/bookmark/report 경로 보호
- Schema/Auth (Gate 4): OAuth redirect URL 설정, `publishPending` 플래그 복원 로직
- Data Bridge (Gate 3): `EncodeSession`의 sessionStorage 직렬화/복원 스펙 필요

## D-06. 공개 취소(Unpublish) UX

### 결정 사항

사용자가 자신의 Response를 공개 취소할 때 거치는 확인 과정과 피드백은 무엇인가?

### 문서에서 언급된 제약

- "소유자는 `/me`에서 자신이 공개한 Response와 bookmark를 확인" (시나리오 7)
- "공개 취소 시 자신의 contribution만 제거. 마지막 기여자라면 Glyph와 관계를 함께 비공개/삭제 처리" (시나리오 7)
- D-03 결정(삭제 cascade 방식)에 의존

### 선택지

| 옵션 | 확인 단계 | 피드백 | 되돌리기 |
|---|---|---|---|
| **A. 2단계 확인 + 되돌리기 안내 (권장)** | 1차: "공개 취소하시겠습니까?" + 마지막 기여자일 경우 경고. 2차: 명시적 "공개 취소" 버튼 | 성공 스낵바 + "30일 내 복구 가능" 안내 | 30일 내 `/me`에서 복구 버튼 |
| B. 1단계 확인 | "공개 취소" 즉시 확인 1회 | 성공 스낵바 | 복구 불가 또는 지원 문의 |
| C. 슬라이드 제스처 | 카드 좌측 스와이프로 삭제 → 확인 없음, undo 스낵바 5초 | undo 스낵바 | 5초 내 undo만 가능 |

### 권장안

**A. 2단계 확인 + 되돌리기 안내.** "마지막 기여자" 경우의 파괴적 결과(Glyph+관계 숨김)를 사전에 명확히 알리고, 소프트 삭제(D-03)와 연동해 복구 기간을 안내한다.

### 후속 영향

- Component (Gate 5): MyArchivePage에 unpublish 확인 다이얼로그, 마지막 기여자 경고 분기, 복구 버튼
- Data Bridge (Gate 3): 남은 활성 기여 수 조회 API

## D-07. 신고(Report) 처리 UX

### 결정 사항

사용자가 부적절한 공개 Glyph를 신고할 때의 인터페이스와 후속 처리 투명성은 어떻게 하는가?

### 문서에서 언급된 제약

- "인증은 PUBLISH, BOOKMARK, REPORT, UNPUBLISH에서만 요구한다" (공개·권한 계약)
- Report 엔티티: `reporterId, glyphId, reason, status` (데이터 모델)
- "신고자와 운영자만 상세 열람" (데이터 모델 활용 표)
- IA: "신고·숨김·unavailable 상태" (공통 영역)

### 선택지

| 옵션 | 신고 입력 | 처리 투명성 | 장점 | 단점 |
|---|---|---|---|---|
| **A. 사유 선택 + 한 줄 메모 (권장)** | 사유 4~5개 라디오 + 선택적 자유 텍스트 1줄 (200자) | 신고 접수 확인만 노출, 처리 결과는 운영 내부 | 사용자 부담 최소, 운영 분류 용이 | 사유 목록 설계 필요 |
| B. 자유 텍스트만 | 이유를 자유롭게 작성 | 신고 접수 확인 | 표현 자유도 | 분류 비용↑, 빈 신고 가능 |
| C. 사유 선택 + 처리 결과 알림 | A와 동일 입력 + 처리 결과를 신고자에게 알림 | 신고 접수 + 결과 알림(이메일 또는 인앱) | 투명성 최대 | 알림 인프라 필요, 초기 운영 부담↑ |

#### 옵션 A 사유 초안

| 사유 코드 | 라벨 |
|---|---|
| `offensive` | 공격적·혐오적 내용 |
| `personal_info` | 타인의 개인정보 포함 |
| `spam` | 스팸·무의미한 반복 |
| `copyright` | 저작권·상표권 침해 |
| `other` | 기타 (메모 필수) |

### 권장안

**A. 사유 선택 + 한 줄 메모.** 초기에는 운영 규모가 작으므로 접수 확인만 제공하고, 이후 필요 시 결과 알림(C)으로 확장한다.

### 후속 영향

- Schema (Gate 4): `reports` 테이블에 `reason` enum + `note` text nullable
- Component (Gate 5): GlyphDetailPage에 신고 버튼 + 사유 선택 다이얼로그
- 운영: 관리자 대시보드는 MVP 범위 외, Supabase Dashboard에서 직접 조회/처리

## D-08. Resonance Field 초기 노출 기준

### 결정 사항

중심 Glyph 기준 8~12개 노출의 구체적 선정·배분 규칙은 무엇인가?

### 문서에서 언급된 제약

- "화면에는 중심 노드 기준 총 8~12개만 노출하고 한 관계 종류가 60%를 넘지 않도록 다양화한다" (후보 검색·노출 제한 4)
- 관계별 저장 상한: FORM 6, ECHO 4, CONTEXT 3, CONTAINS 6 (후보 검색·노출 제한 3)
- "기준을 통과한 관계가 없으면 강제 연결하지 않는다" (후보 검색·노출 제한 5)
- "관계 0개 → FIRST OF ITS CONTOUR + 새 이름 인코딩 CTA" (시나리오 6, 예외)
- 내러티브 원칙 4: "고립도 세계관으로 수용"

### 선택지

| 옵션 | 배분 규칙 | 장점 | 단점 |
|---|---|---|---|
| **A. 점수 내림차순 + 60% 캡 (권장)** | 모든 관계를 점수 내림차순으로 정렬. 상위부터 채우되, 특정 유형이 60%에 도달하면 해당 유형 스킵하고 다음 유형에서 채움. 총 12개 또는 후보 소진 시 중단 | 단순, 최고 점수 관계 우선 | 관계 수가 적은 유형이 밀릴 수 있음 |
| B. 유형별 쿼터 | FORM 4, ECHO 3, CONTEXT 2, CONTAINS 2, VARIANT 1 = 12개 고정 쿼터. 쿼터 미달 시 다른 유형으로 재배분 | 다양성 보장 | 높은 점수 관계가 쿼터에 밀려 제외될 수 있음 |
| C. 2단계 | 1단계: 유형별 최고 1개씩 우선 배치(최대 5개). 2단계: 나머지 슬롯을 점수 내림차순으로 채움(60% 캡 적용) | 모든 유형 최소 1개 보장 + 고점수 우선 | 구현 약간 복잡 |

### 권장안

**A. 점수 내림차순 + 60% 캡.** 가장 단순하고 "연결 이유"를 강조하는 세계관과 일치한다. 아카이브 초기에는 관계 수 자체가 적으므로 쿼터 방식은 오버엔지니어링이다.

### 후속 영향

- 관계 로직: 노출 선정 로직을 클라이언트(ResonanceFieldPage)에서 처리할지, 서버(Edge Function/DB 뷰)에서 처리할지 결정 필요 → Gate 3(Data Bridge)
- Component (Gate 5): ResonanceMap에 "관계 없음" 상태(FIRST OF ITS CONTOUR) UI 필요
- 모바일: 12개 노드 동시 렌더 시 성능 상한 → Gate 6(통합 검증)에서 실측

## D-09. 인증 provider 및 최소 프로필

### 결정 사항

어떤 인증 방식을 지원하고, 가입 시 수집하는 최소 프로필 정보는 무엇인가?

### 문서에서 언급된 제약

- Profile 엔티티: `handle, displayName, avatarUrl, status` (데이터 모델)
- "공개 프로필에는 이메일·인증 provider 같은 Auth 정보를 포함하지 않는다" (공개·권한 계약)
- "기여자 신원 대신 기여 수만 노출한다" (데이터 모델 카드 C)

### 선택지

| 옵션 | Provider | 프로필 수집 | 장점 | 단점 |
|---|---|---|---|---|
| **A. Google OAuth 단일 (권장)** | Google만 | 표시 이름(OAuth에서 기본 가져오기), 아바타(선택) | 구현 최소, 대부분 커버 | Apple 미지원 불만 가능 |
| B. Google + Apple + 이메일 | 3종 | 표시 이름 필수, 아바타 선택 | 커버리지 최대 | 구현·유지 비용↑ |
| C. 매직 링크(이메일) 단일 | 이메일 매직 링크 | 표시 이름 가입 시 입력 필수 | 소셜 로그인 없이 프라이버시↑ | UX 마찰↑ (메일함 이동) |

### 권장안

**A. Google OAuth 단일로 시작.** MVP에서 단일 provider로 빠르게 출시하고, 수요에 따라 Apple/이메일을 추가한다. 표시 이름은 OAuth에서 가져오되 수정 가능. handle은 auto-generate(publicId 형식).

### 후속 영향

- Schema/Auth (Gate 4): Supabase Auth에 Google provider 설정, `profiles` 테이블에 가입 트리거
- Component (Gate 5): LoginForm은 Google 버튼 1개 + 선택적 이름 편집

## D-10. Unavailable/숨김 상태 UX

### 결정 사항

삭제·숨김·신고 처리된 Glyph의 URL에 접근할 때 어떤 화면을 보여주는가?

### 문서에서 언급된 제약

- "숨김·삭제된 Glyph → 이름과 모델을 노출하지 않는 unavailable 상태" (시나리오 7, 예외)
- IA: "신고·숨김·unavailable 상태" (공통 영역)

### 선택지

| 옵션 | 화면 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 세계관 톤의 unavailable (권장)** | 로고그램·이름 없이 "이 응답은 아카이브에서 제거되었습니다" + 새 인코딩 CTA | 세계관 일관, 정보 최소 노출 | 제거 사유 불투명 |
| B. 404 페이지 | 일반적인 "페이지를 찾을 수 없습니다" | 구현 최단순 | 세계관 이탈 |
| C. 사유 포함 | "이 응답은 [작성자 요청 / 운영 정책]에 의해 제거되었습니다" + 재인코딩 CTA | 투명성↑ | 사유 분기 구현 필요, 신고 처리 사유 노출 시 갈등 소지 |

### 권장안

**A. 세계관 톤의 unavailable.** 안개 배경 + 최소 메시지로 세계관을 유지하면서 개인정보(이름)를 완전히 제거한 화면. 사유는 운영 내부에서만 관리한다.

### 후속 영향

- Component (Gate 5): GlyphDetailPage에 `unavailable` 상태 분기 렌더링
- Schema (Gate 4): `glyphs.status`에 `hidden` | `deleted` 상태 필요
