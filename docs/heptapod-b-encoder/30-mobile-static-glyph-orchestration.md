# 모바일 정적 표식 전환 — 병렬 실행 설계

작성일: 2026-09-09. 상태: 사용자 실행 지시에 따라 A/B/C 구현 및 통합 진행. 세부 규격은 mobile-static-glyph-contract.md, 적용 결과는 31-mobile-static-glyph-results.md 참조.

## 결정과 완료 조건

공통 규격을 먼저 확정한 뒤 **루트 1명 + 작업자 3명**, 최대 4개 슬롯으로 진행한다. 이미지 렌더러, 저장·생성 파이프라인, 모바일 UI는 규격과 fixture가 있으면 서로 다른 파일에서 진행할 수 있다. 기존 DB 일괄 변환은 렌더러와 파이프라인이 합쳐진 뒤 실행해야 한다. 에이전트별 별도 매니저나 하위 에이전트는 두지 않는다.

완료 조건:

- 모바일의 개인 표식 상세 예외를 제외한 표식은 실제 이미지 요소로 표시한다. 정지 Canvas로 대체하는 것으로 완료 처리하지 않는다.
- 기존 저장 모델을 보존하면서 기존 공개 표식 전체의 이미지 상태를 집계하고, 새 공개 표식도 자동으로 이미지를 생성한다.
- 이미지 준비가 끝난 표식은 목록 진입 시 입자 생성·Canvas 그리기를 수행하지 않는다. 상세 진입·복귀·공유·분석은 정상 동작한다.
- 모바일 아카이브 메인 2×2, 세로 항목 구성, 시간순 원형 표식, PC의 기존 레이아웃·렌더링을 유지한다.
- 화면 검사와 성능 실측을 구분한다. 비브라우저 테스트 통과만으로 모바일 FPS 개선을 확정하지 않는다.

다음은 실행 준비에서 확인할 전제이며 현재 운영 상태를 확인했다는 뜻은 아니다.

- 모바일 기준은 기존 테마의 `md` 미만, 현재 900px. PC 터치 기기를 일괄 모바일로 분류하지 않는다.
- 개인 상세는 `/glyph/:id`, 아카이브의 선택 상세, 개인 생성 결과의 상세·분석 영역을 포함한다고 가정한다. 상세 화면 내부는 기존 렌더링을 유지한다. 루트는 실행 시작 시 사용처 표에 이 경계를 명시한다.
- 개인 생성 결과 밖의 미저장 모델은 A가 제공하는 Worker에서 한 번 이미지로 변환하고 C가 모델 해시별 Blob을 재사용한다. 저장되지 않은 이름·모델을 임의로 서버에 보내지 않는다. Worker 실패 시 정적 오류 상태를 유지하며 Canvas 루프를 자동 활성화하지 않는다.
- 현재 운영 DB의 전체 개수·모델 버전 분포·기존 Storage 버킷·백그라운드 작업 실행 환경은 미확인이다. 개수나 작업 시간을 추정값으로 확정하지 않는다.
- 원본 `model_data`, 이름, UUID, 의미 분석, 관계 데이터는 보존한다. 이미지는 파생 데이터다.
- 브라우저·Playwright·Chrome MCP 자동화는 사용자 명시 요청 전까지 금지한다. 로컬 파일 검사, Node 테스트, 이미지 파일 직접 보기, 허용된 환경의 HTTP 검사만 사용한다.

## G0 — 루트가 먼저 확정할 계약

1. **사용처 표:** `ArchiveGlyph`, `GlyphNode`, 직접 `LogogramRendererCanvas` 호출을 조사하여 `personal-detail / public-glyph / authored-symbol / local-model`로 분류한다. 경로 문자열만으로 예외를 판단하지 않고 공유 상세 컴포넌트에 명시적인 렌더링 범위를 둔다.
2. **이미지 규격:** 투명 배경의 정사각형 WebP를 우선 후보로 정하고 256·512px 두 크기를 비교한다. 잉크·미세 입자·여백·중심 좌표를 동일 모델 기준으로 검증한 뒤 인코딩 설정을 고정한다. 이름은 이미지에 굽지 않는다. 크기는 검증 전 후보이며 실제 모바일 표시 크기와 DPR에 맞춰 최종 확정한다.
3. **식별:** `glyphId + canonicalModelHash + rendererVersion + size + inkVariant`를 파생 이미지 키로 사용한다. `meta.hash`만 사용하지 않는다. 내용 해시의 정규화 방법과 렌더러 버전을 계약 파일에 고정한다.
4. **상태:** `pending / processing / ready / failed / unsupported`와 크기별 준비 상태를 구분한다. 필수 크기 업로드와 검증이 끝난 후에만 `ready`로 공개한다. 원본 표식 레코드 삭제·덮어쓰기를 하지 않는다.
5. **보관·접근:** DB 표식 이미지는 비공개 Storage에 저장하고 공개 상태를 확인하는 서버 경유로 전달하는 방식을 기본으로 한다. 장기 공개 CDN URL로 현재의 공개 취소 동작을 약화시키지 않는다. 서버의 생성 결과 재사용과 HTTP 캐시 정책을 구분한다. 재검증 없는 브라우저/CDN 캐시는 도입하지 않는다. 고정 저작 표식만 버전 경로의 공개 정적 파일로 배포한다.
6. **자동 생성:** 공개 성공과 내구성 있는 작업 등록을 연결한다. DB 작업 큐·중복 방지·lease·제한된 재시도·실패 상태를 계약으로 둔다. 배포 환경에서 실제로 계속 실행될 소비자와 호출 권한을 확인해야 하며, 요청 종료 후 소실되는 비동기 함수나 방문자 접근만으로 작업을 처리하지 않는다.
7. **API:** 미저장 모델 경로는 브라우저 Worker의 `model + options → image bytes` 계약을 추가하며 캐시 크기 제한·Blob URL 해제를 포함한다. 작업자 A는 `renderGlyphImage(model, options) -> { bytes, width, height, mimeType, checksum }`, B는 `getImageDescriptor(glyphId) -> { status, modelHash, rendererVersion, variants }`, C는 `StaticGlyphImage`와 명시적인 상세 예외 경계를 구현한다. 계약·정상/실패 fixture는 루트가 먼저 만든다.
8. **미준비 처리:** 자동으로 Canvas로 돌아가 목록 전체를 다시 계산하지 않는다. 같은 공간과 이름·상세 진입을 유지하는 placeholder 및 재시도를 사용한다. 일괄 생성 커버리지를 확보한 뒤 모바일 전환을 켠다. 사용자에게 이미지 준비 상태를 어떻게 표시할지는 기존 UI 문구 규칙 안에서 확정한다.

계약은 `src/lib/glyphImages/contract.js`와 `docs/heptapod-b-encoder/mobile-static-glyph-contract.md`에 루트가 단독 작성한다. 현재 문서는 이 파일들을 만들었다는 뜻이 아니다.

## 실행 파동과 합류 기준

```text
G0 계약·fixture·실행 환경 확인
  ├─ A 이미지 렌더러·고정 asset ─┐
  ├─ B 저장·작업 큐 소비자 ─────┼─ G1 통합 ─ G2 기존 데이터 처리 ─ G3 전환 검증
  ├─ C 모바일 UI ─────────────┤
  └─ 루트 스키마·데이터 연결 ───┘
```

1. **준비:** 루트가 G0를 완료한다. 특히 소비자가 지속 실행되는 방식이 불명확하면 B에게 운영 자동화가 완성되었다고 간주하게 하지 않는다. 로컬 fixture 기반 작업과 운영 환경 확인을 분리한다.
2. **병렬 구현:** A/B/C를 함께 시작한다. B는 A의 렌더러 대신 stub, C는 B의 fixture를 사용해 독립적으로 진행한다. 루트는 migration·공개 함수의 작업 등록·조회 DTO·회귀 기준을 구현한다.
3. **첫 합류:** A의 실제 이미지와 manifest, B의 재시도 가능한 저장·접근 경로, C의 분기 및 DOM 검사가 모두 있어야 한다. 루트가 stub을 실제 구현으로 교체하고 이미지 중심·크기·잉크·상태 응답을 검사한다. 불일치는 G0 계약에 대조하여 루트가 결정한다.
4. **일괄 처리:** 로컬 fixture dry-run → 실행 대상과 예상 생성량 manifest → 기존 공개 행 생성 → 실패 재시도 → 신규 등록 및 공개 취소 동시 발생 검사를 수행한다. 운영 DB·Storage 적용과 배포는 그 시점에 확보된 사용자 실행 범위 안에서만 수행한다. 지금 계획 요청은 운영 쓰기 권한이 아니다.
5. **최종 합류:** 기존 데이터 처리 결과와 신규 작업 자동 소비 증거가 있어야 모바일 기능을 활성화한다. UI 먼저 전환해 빈 이미지를 대량 노출하지 않는다. 루트가 직접 최종 통합 테스트를 실행한다.

## 그대로 전달할 작업자 브리프

모든 브리프의 공통 계약: 다른 작업자가 같은 저장소에서 작업합니다. 기존 미커밋 변경과 다른 작업자의 수정을 보존하고, 충돌 시 되돌리지 말고 루트와 소유권을 조정하십시오. G0 계약과 fixture를 먼저 읽으십시오. 브라우저 자동화·원격 쓰기·배포·에이전트 추가 생성은 이 브리프의 권한이 아닙니다. 인계는 `변경 경로 / 계약 준수 / 실행한 검사와 결과 / 미해결 위험` 순서로 작성하십시오. 계약을 깨는 문제가 발견되면 종속 변경을 중단하고 루트에 보고하되 독립 작업은 계속하십시오.

### A — 이미지 렌더러

> 목표: 저장된 모델의 형태를 재현하는 투명 정적 이미지와 저작 표식 asset을 생성하십시오. 모바일 계산을 서버·빌드 시점으로 옮기는 독립 모듈입니다. 입력은 G0 계약, `logogramParticles.js`, 기존 `src/lib/og/png.js`, 계열·유형 저작 모델입니다. 소유권은 작업 표 A의 파일만입니다. OG 코드·공통 입자 엔진·DB·UI·package/lockfile은 수정하지 마십시오. 기존 모델을 이름으로 재인코딩하지 마십시오. 시간순의 빈 clusters와 부분/구형 모델을 별도로 검증하고 불명확한 모델은 unsupported로 보고하십시오. 미저장 모델은 같은 형태 규격의 로컬 Worker 이미지 바이트로 반환하되 브라우저 코드에 Node 전용 모듈을 포함하지 마십시오. 소비자는 B/C와 루트입니다. 완료 기준은 결정성, 투명 배경, 중심·여백·파편 마스크 좌표 일치, 모델 복잡도 제한, 한·영 이름 유무와 무관한 표식 형태 보존입니다. 후보 크기별 파일 용량·서버 생성 시간·대표 PNG 비교 이미지를 반환하십시오. 브라우저를 사용하지 마십시오.

### B — 저장·생성·기존 데이터 처리

> 목표: A의 이미지 생성기를 주입받는 저장 서비스, 접근 API, 내구성 작업 소비자, 재개 가능한 backfill 명령을 구현하십시오. 렌더러와 독립적으로 상태·재시도·공개 취소를 검증하는 작업입니다. 입력은 G0 계약과 루트의 migration 초안이며, A 완성 전에는 결정적 stub을 사용하십시오. 작업 표 B의 파일만 수정하고 migration·Edge 공개/취소 함수·UI·공통 계약은 직접 수정하지 마십시오. 연결 변경은 루트에게 전달하십시오. Storage 접근은 adapter로 격리하고 local dry-run이 기본이어야 합니다. backfill은 최근 200개가 아닌 전체 대상을 안정된 키 순서로 페이지 처리하고 checkpoint, 항목별 결과, 재실행 skip, 제한된 동시성, 실패 재시도를 제공해야 합니다. model hash가 변경되거나 공개 취소된 작업은 업로드 후에도 ready 전환 전에 재검증하십시오. 공개 취소 뒤 기존 이미지 URL도 새 요청에 대해 차단되어야 합니다. 소비자는 C와 루트입니다. 완료 기준은 로컬 계약 검사 및 실패/중복/중단 후 재개/공개취소 경쟁조건 검사입니다. 운영 호출이나 업로드는 하지 마십시오.

### C — 모바일 화면 적용

> 목표: 모바일의 개인 상세 예외를 제외한 표식을 실제 이미지로 바꾸고 PC 동작을 보존하십시오. 저장 서비스와 독립적으로 화면 분기·탐색·레이아웃을 구현하는 작업입니다. 입력은 G0 사용처 표와 이미지 fixture이며 작업 표 C의 파일 및 대응 stories만 수정하십시오. DB·API·ArchiveDepthExplorer·공통 테마·전역 Lenis·랜딩 비디오는 수정하지 마십시오. 세부 사용처를 추가로 발견하면 루트에게 경로를 보고하십시오. 상세 예외는 `/glyph`와 아카이브 선택 상세의 공유 컴포넌트 경계에 두십시오. 모바일 정적 분기는 처음부터 live Canvas와 입자 계산을 마운트하지 않아야 합니다. 이미지 크기 예약, 필요한 해상도 선택, lazy load, async decode, 실패 상태, 긴 이름, 클릭·키보드·접근성 이름을 보존하십시오. CSS의 `& canvas` 조건과 분석/부분 마스크가 이미지에서도 맞는지 점검하십시오. 미저장 모델은 A의 Worker를 호출하고 해시별로 캐시하여 메인 스레드 입자 계산을 피하십시오. 캐시와 Blob URL의 수명을 제한하고 개인정보를 자동 전송하지 마십시오. 소비자는 루트입니다. 완료 기준은 320/390/768/899/900/1440px의 SSR·인메모리 DOM 검사, 상세 진입·복귀 검사, 미리 생성된 표식의 입자 생성/Canvas draw 호출 0, 미저장 모델의 메인 스레드 입자 생성 0 및 재사용 시 Worker 재생성 0입니다. 시각 렌더 완료나 FPS 향상은 별도 측정 없이 주장하지 마십시오.

## 루트 검증과 실패 처리

- **소유권:** 시작 전 현재 diff를 기록하고 합류 시 경로별로 비교한다. 공유 파일 충돌은 루트가 통합하며 파일 전체 되돌리기를 금지한다.
- **이미지 품질:** 세 계열·시간순·유형 상징, 질문형·간극·농담·밀집 모델·기존 버전 등 대표 표식을 로컬 이미지 파일로 비교한다. OG 이미지는 참고이며 최종 Canvas 형태와의 일치를 별도로 확인한다. AI 이미지 생성으로 표식을 재해석하지 않는다.
- **UI 회귀:** `test-mobile-archive-layout`, `test-archive-field-state`, `test-archive-mobile-observation`, `test-glyph-node-work`, 관련 정적 이미지 검사, 대상 ESLint와 Next build를 실행한다. 형식상 Canvas 존재를 요구하던 테스트는 사용자 동작을 보존하는 방향으로 갱신한다. 검사 삭제로 통과시키지 않는다.
- **작업·데이터:** 테스트 DB/Storage adapter에서 등록·실패·재시도·공개 취소·모델 변경·오래된 버전 요청을 검증한다. 전체 조회는 고정 시작점과 후속 신규 작업 큐를 함께 확인한다. `대상 = ready + failed + unsupported + 실행 중 제외된 항목`이 맞는지 집계하고 각 제외 이유를 기록한다. 미생성 정상 대상이 남았으면 전체 완료로 보고하지 않는다.
- **성능 증거:** 동일 fixture에서 미리 생성된 표식 목록의 입자 생성/Canvas draw 0, 로컬 미저장 표식의 메인 스레드 계산 0 및 Worker 최초 변환 시간, 이미지 전송량·디코딩 크기, 최초 생성과 재사용 시 서버 작업량을 기록한다. 실제 모바일 스크롤 FPS·발열·장시간 메모리는 추후 허용된 실기기 측정 항목으로 남긴다. 모델 JSON 조회·의미 계산·안개 효과 비용까지 해결됐다고 주장하지 않는다.
- **A 실패:** 기본 표시를 전환하지 않고 품질 문제 모델과 검증기를 수정한다. B/C는 fixture 작업을 지속한다. 지원 불가 데이터의 원본을 추측하여 변경하지 않는다.
- **B 실패:** UI를 운영에 켜지 않고 로컬 저장 adapter로 통합을 마친다. 실행 환경 미비는 실제 자동 소비가 해결될 때까지 배포 미완료로 기록한다.
- **C 실패:** 생성된 이미지는 유지하고 모바일 전환만 비활성화한다. PC로 수정 범위를 확대하여 해결하지 않는다.
- **병렬 수행 불가:** 같은 계약을 유지하며 루트가 A → B 및 데이터 연결 → C → backfill·통합 검증 순서로 수행한다. 중복 구현이나 소유권 없는 긴급 수정을 만들지 않는다.

최종 인계물은 구현 diff, 이미지 manifest, 전체 데이터 변환 집계, 자동 생성·취소 검사 결과, 모바일/PC 회귀 검사 결과, 실측하지 못한 성능 항목이다.
