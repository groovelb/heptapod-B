## 목표와 전제

이름 생성 → 공개 동의 → 익명 세션으로 등록 → 공개 페이지 열기·주소 복사·공유 → 보관한 링크로 재방문까지 동작하게 한다.

- Google을 포함한 소셜 로그인, 이메일 가입, 계정 연결은 요구하지 않는다. 기존 문서의 Google/manual linking 활성화 지침보다 이번 사용자 요구가 우선한다.
- 기존 `/glyph/:id` 계약을 유지한다. 같은 이름·표현은 동일한 표식 페이지를 공유한다. 사용자별 고유 프로필은 이번 범위에 포함하지 않는 전제다.
- 공개 링크는 열람용이다. 링크 소지만으로 등록자의 관리 권한을 부여하지 않는다. 익명 세션이 없어져도 공개 중인 페이지는 볼 수 있다.
- 사용자가 링크를 직접 보관하는 UX다. 새 계정 복구 체계나 개인 목록 저장 기능을 추가하지 않는다.
- 현재 라우트 이동 시 생성 상태를 메모리에 보존하는 코드가 있다. 이를 유지하되 새로고침 이후의 재방문은 공개 링크로 검증한다.
- 브라우저 자동화는 금지한다. Node, happy-dom, SSR, Deno, SQL, HTTP로 검증한다. 실제 모바일 공유창·픽셀·포커스 검증은 별도 명시적 요청 전까지 수행하지 않는다.

## 분할 결정

루트 1 + worker 2, 최대 동시 3개를 사용한다. 환경 한도 4개 중 1개는 비워 둔다. 서버 산출물과 UI 산출물은 파일 소유권이 분리되고 `glyphId` 계약을 유지하므로 병렬 작업이 유효하다. 운영의 공유 상태 변경은 병렬화하지 않는다.

| ID | 담당 | 소유 범위 | 선행 조건 | 산출물·완료 검사 | 주요 위험 |
|---|---|---|---|---|---|
| P | 루트 | 현황·인터페이스·기존 diff 기준 | 없음 | 프로젝트/환경/호스팅 대상과 파일 소유권 확정 | 다른 작업의 변경과 혼동 |
| B | worker: backend | `supabase/config.toml`, `supabase/functions/**`, `supabase/migrations/**`, `supabase/tests/**`의 로컬 파일 | P | 배포 가능한 서버 코드·SQL, 로컬 권한/중복/철회 검사 | 기존 데이터·권한 영향 |

## 진행 단계와 합류 조건

1. **준비 P:** 기존 변경을 기록한다. 현재 원격 상태, 사용 중인 클라이언트 버전, 호스팅 도메인·SPA rewrite·배포 수단을 읽기 전용 확인한다. 입력 `{ displayName, contextTags, consented }`, 성공 응답의 `glyphId`, 공개 URL `/glyph/:id`를 공통 계약으로 고정한다. 호스팅 대상이 로컬 정보로 확인되지 않으면 그 정보만 질문하고 독립적인 로컬 작업은 계속한다.
2. **병렬 B + U + V:** B는 로컬 서버 산출물, U는 링크 보관 UI, 루트는 테스트와 운영 반영 절차를 준비한다. 원격 쓰기는 하지 않는다.
3. **합류 J:** 각 담당자의 변경 파일·검사 결과·남은 문제를 받는다. 루트가 파일 소유권과 diff, API 계약을 확인하고 전체 시나리오를 재검사한다. 필요한 백엔드/UI 계약 변경은 루트가 결정하여 의존 작업을 순서대로 수정한다.
4. **운영 R:** 검증된 통합본과 정확한 SQL·설정·함수·호스팅 대상이 준비된 뒤 운영 반영 범위를 확정한다. 실행 요청에 배포 권한이 이미 포함돼 있으면 반복 확인하지 않는다. 포함되지 않았다면 이 구체적 산출물을 기준으로 최종 승인을 받는다.
5. **원격 검증:** 운영 설정·권한·함수·페이지 URL을 직접 확인하고 승인된 테스트 데이터로 등록부터 재방문까지 확인한다. 이 단계 전에는 연동 완료로 보고하지 않는다.

운영 적용 순서는 **권한 마이그레이션 → 함수 배포 → 익명 로그인 활성화 → 프론트 배포 → 원격 검증**으로 한다. 구형 프론트가 직접 쓰기를 한다면 권한 차단 이후 등록이 실패할 수 있으므로 준비된 새 프론트를 연이어 전환한다. 쓰기 권한을 다시 공개하는 방식으로 장애를 우회하지 않는다.

> 검증: 기존 component-work 규칙과 client 주입 유지, 성공/등록 실패/공유 취소·실패/복사 실패 상태의 Storybook 사양 동기화 및 정적 검사. 브라우저 없이 작업하고 상호작용 통합 검사는 루트 V가 담당한다.
>
> 완료: 모든 성공 진입 경로에서 사용자에게 주소가 보이고 페이지 열기·독립 복사·수동 보관이 가능하다. API 계약 변경이 필요하면 먼저 루트에 보고한다.
>
> 반환 형식: 변경 경로 / 상태별 동작 / 검증 결과 / 루트가 검증할 선택자·스토리 / 미해결 위험. 소비자는 루트 J/V이다.

## 루트의 검증·완료 판정

- 잘못된 테스트 기대값을 실제 표시 의미에 맞춰 수정한다. 실패를 건너뛰거나 assertion을 삭제하여 통과시키지 않는다.
- 빌드, 변경 파일 lint, 기존 데이터/공유/SQL/Edge 검사와 인코더 happy-dom 테스트를 실행한다. 등록·공유 부분까지 도달했는지 확인한다. `check-agent-rules`는 현재 script가 없으므로 누락 사실을 기록한다.
- 등록 전에는 사용자 이름이나 새 익명 계정을 서버에 만들지 않는지 확인한다. 동의 후 세션 자동 생성, 기존 세션 재사용, 이름 유지·재시도를 검증한다.
- 운영에서는 익명 가입 설정, 함수 응답, 마이그레이션 이력, RLS와 GRANT를 재조회한다. 설정 파일의 true만으로 완료 판정하지 않는다.
- 승인된 별도 테스트 이름으로 실제 등록 성공, 재시도 시 동일 glyphId, 인증 없는 별도 HTTP client로 공개 조회를 확인한다. 테스트 레코드 ID를 기록하고 테스트 데이터만 정리한다. 기존 기여나 운영 사용자 데이터는 변경하지 않는다.
- 다른 소유자의 철회 불가와 마지막 기여 철회 후 비공개를 먼저 격리된 SQL 테스트에서 확인한다. 운영 검증이 필요한 경우 별도 테스트 소유자/레코드에 한정한다.
- 실제 서비스의 `/glyph/:id` 직접 GET이 앱 HTML을 반환하고, 해당 표식을 인증 없이 조회하는지 확인한다. 프론트 도메인·rewrite 확인 전에는 외부 공유 완료로 간주하지 않는다.
- 운영 `api` 관계 계산이 성공하는지 확인한다. 개발 `local` 성공과 구분한다. 리치 OG 이미지는 이번 기본 링크 공유의 필수 완료 조건에 포함하지 않는다.
- 합류 시 기존 diff와 담당별 diff를 비교한다. 다른 담당 파일 변경이나 stale 파일 덮어쓰기가 있으면 해당 소유자와 해결한 후 검사한다. agent 완료 메시지 자체는 검증 근거로 대신하지 않는다.
- 최종 보고에는 로컬 통과/원격 통과/실제 브라우저에서 미확인인 항목을 구분한다. 사용자가 요청한 전체 시나리오의 원격 검증이 끝나야 'Supabase 연동 완료'로 보고한다.

## 실패 시 처리

- B 지연/실패: U는 client fixture로 계속한다. 루트가 서버 작업을 순차 인수하고 해결 전 운영 전환을 보류한다.
- U 지연/실패: B는 배포 준비까지 완료한다. 루트가 UI를 인수한다. 링크 보관 경로 없이 전체 완료를 선언하지 않는다.
- 원격 권한·설정 접근 불가: 로컬 통합본, 검사 결과, 실행할 SQL/설정/배포 목록을 완성한 뒤 꼭 필요한 접근만 요청한다.
- 운영 장애: 마지막 검증된 코드로 복구하거나 추가 수정한다. 마이그레이션 역적용으로 공개 쓰기 권한을 복원하거나 기존 데이터를 삭제하지 않는다.
- 병렬 슬롯 사용 불가: 같은 계약과 순서로 B → U → V/J → R을 루트가 순차 실행한다.
